# 008：60fps 顯示排程

狀態：CONFORMED，2026-11-11。使用者要求流暢度支援 60fps；READY 契約實作後通過以下驗收。

## 證據與範圍

這是重製版前端的顯示排程與效能修正。既有 [規格 001](001-rust-first-stage.md) 已定案邏輯每秒約 9.10 次、畫面補間；[規格 007](007-manual-posters.md) 已定案兩組海報構圖。本次不改遊戲規則、速度、存檔、海報尺寸、構圖與像素。

| 目前事實 | 證據等級與出處 |
|---|---|
| 有垂直同步時僅以 2ms 作最低等待，未明確限制 60fps；沒有同步時是 16ms，即 62.5fps | 靜態已證實，`app.rs::window_loop`，修正前提交 `91fd9e1` |
| 每幀重做左右海報縮放 | 靜態已證實，`view.rs::draw_posters`，同上 |
| 同容器、軟體繪圖器，6 秒展示：無海報 373 幀，現代海報 322 幀；邏輯均 55 步 | 動態已證實，`workspace/rs2/fps-before-off.log`、`fps-before-modern.log`，約 62.2／53.7fps |

工具為 Rust 1.99.1、既有 `mm45-rust-desktop:1.99.1-r3`、Xvfb 1920×1200、SDL software renderer；容器 4 CPU、3GiB。原始執行程式 SHA-256 `ea9f29c3d62991d5381aec31ef568cb0ad7e3aca09c320b9df52c01be8148920`。海報輸入雜湊沿用規格 007。位址空間為單調計時器與前端視窗像素；沒有新增原版位址、機器碼語意或硬體驅動研究。

## 行為契約

- 新增獨立 `DisplayClock`，以 SDL 單調計時器按每秒 60 個顯示時槽排程。第一幀立即顯示，後續截止時間從固定起點計算，避免 16666／16667 微秒取整誤差長期累積。
- 保留 `Pacer` 的每步 ticks、最多補步、暫停與恢復處理。輸入與邏輯照原本流程輪詢，不等到顯示幀才處理。
- 垂直同步仍可啟用，但不能只憑繪圖器旗標判定幀率。顯示排程將較高更新率與未真正等待的驅動限制於 60fps 目標。硬體或繪製成本不足時容許掉幀，不把漏掉的畫面補播成短暫高速，也不加速遊戲。
- 補間預設維持開啟。VGA／HD 依現有物件補間與玩家機預測繪製中間位置。補間關閉及 CGA／MGA 保留既有動作節奏，不把重複呈現稱為新增 60 格動畫。
- 靜態海報於組別、實際顯示尺寸或繪圖裝置改變時重建縮放快取；平常以 1:1 貼回。快取畫法必須與原本逐幀縮放的輸出逐像素相同。繪圖器不支援目標貼圖或建立失敗時回退原畫法，不改圖或阻止遊戲啟動。
- 桌面與手機都記錄每五秒的實測顯示幀率，結束時記錄平均值；量測結果不作任意硬體的 60fps 保證。靜止、暫停或未開補間時可以減少重畫。

資料與垂直鏈：既有資產／模擬步進 → 原補間 → 顯示時槽 → SDL／海報快取 → 正常玩家畫面。遊戲設定與存檔格式無變動，不新增正式玩家旗標。

## 驗收

1. `DisplayClock` 固定時鐘測試：60Hz、不同計數器頻率、60 秒無漂移、低更新率／長停頓不補播；與原 `Pacer` 並行時邏輯步數及補間進度一致。
2. SDL 真實海報測試：新舊畫法逐像素相同，涵蓋兩組、視窗大小、裝置重建；不支援快取時回退。
3. 在同一個 Docker／Xvfb／軟體繪圖環境重跑海報開關的速度測量，記錄有效秒數與幀率，不將快速入口效能量測當作正常玩家路徑。
4. 用既有標題入口 GUI 海報腳本抽測第一關、切換、保存、重開，並保留五種顯示組合的同輸入模擬檢查。
5. 建置、相關測試、外洩閘門、檔案擁有權與容器清理通過。完成聲明限於本機前端，不變更已發布 tag、Release 或舊封包。

重跑入口：`tools/rust.sh play-test pacer::`、`tools/rust.sh play-test poster_cache_is_pixel_identical`、`tools/rust.sh play-build`、`tools/rust.sh play-fps-check`。效能與正常玩家路徑由 [fps_verify.py](../../tools/fps_verify.py) 執行，收據留在本機 `workspace/rs2/fps-verification/`，拒絕覆寫既有批次。

原版沒有此 60fps 顯示排程，原版 oracle 不適用於新增的顯示時槽。原有模擬一致性與補間測試繼續作為不改玩法的驗證，不新增原版 parity 聲明。
