### 三種執行配置

| 配置 | 做法 | 對應 |
|---|---|---|
| A | 先跑 `ASMDRV.EXE`，用 dosgolem 的監督佇列與 `int 21h AH=31h` 讓它常駐，再接 `S.EXE`；`-adlib` 讓 OPL2 偵測成功 | `RS2.BAT` 的順序，AdLib 存在。路徑 A，不需要改 dosgolem |

### 位址與時間

- 腳本與日誌的遊戲位址一律是 IDA 線性位址（映像基底 `10000h`）。驅動在遊戲 INT 8 或 INT 9 向量指到 `CS:A7B5`／`CS:A83D` 時，取該 `CS` 的線性位址為基底，執行期位址 = 基底 + (IDA − `10000h`)。A 配置基底為 `05110h`，B 配置為 `01100h`。
- 虛擬秒 = 送出的 IRQ0 數 ÷ PIT 通道 0 當下頻率，累加。頻率來自程式寫進 8254 的除數，不是 18.2 Hz 的推算。`StepsPerSecondNow()`（`IRQ0Every × PITHz`）在三種配置都是每秒約 11.58 M 道指令（量到 11,580,826～11,580,906）。計時器沒有釘死（不用 `-tick`），兩個時間基準一致。
- IF 關著時合併掉的 IRQ0 不補。三種配置的量測窗口以 15 秒計，誤差在 ±1 個 tick。
- 輸入走 IRQ1（埠 60h）。遊戲本體沒有任何 `int 16h` 呼叫，只有破解組 intro 讀 BIOS 緩衝區。

### 破解組 intro

- 起始就送鍵的 `cmd/run -keys v` 在 6,000 萬步後仍停在 `0A79:08BD`。intro 在 `1A2BA` 先 `int 16h AH=0` 讀走按鍵，再檢查 `byte_19D67`（`sub_19D44` 每個垂直回掃加 1，數到 `0FAh` 才放行）。回掃計數不足時鍵被讀走丟掉。等級：現象動態已證實，機制靜態已證實。
- 第 45,000,000 步以 BIOS 鍵送 `v` 即可通過。之後 intro 跳進內層 stub，遊戲自己裝 INT 9（`1A83Dh`）與 INT 8（`1A7B5h`）（`vec` 事件，步 45,587,882～45,587,907）。

### 文字選單

- V、E、C、H 設定 `byte_1CF74／1CF75`：V = `E`,`N`；E = `E`,`Y`；C = `C`,`N`；H = `H`,`N`（`mode_v/e/c/h`）。E 模式才是純 EGA 調色盤，與 `CONTEXT.md` 的術語一致。
- 按 V 後遊戲立刻開 `A.MIX`（步 70,000,272）。

### 密碼畫面

- 三列各有 `RED WHITE YELLOW BLACK BLUE`。左（4Bh）右（4Dh）選色，Enter（1Ch）或空白（39h）確認，一列確認後進下一列（`sub_1097D`）。

### 從標題進遊戲

- 開場（`BEG1`）期間任何鍵都進正式遊戲：按鍵當下開 `J1.GO`，PIT 回到 65536（音樂停止），J1 畫面等第二次按鍵，之後開 `BH1.GO`、`SHT1.GO`、`DM1.LCK`、`B.MIX`，第一關開始。

- 不按鍵時的循環（`demo`）：開場與標題（`A.MIX` 載入起約 13 秒）→ `DM1` 展示（22.2～106.6 秒）→ `DM2` 展示（106.6～146.8 秒，幀 0～366）→ 開場。`DM1` 到 `DM2` 之間沒有重新載入 `A.MIX`，`DM2` 結束時才重新開場。

  - CTRL 選 2（2 PLAYERS）後開始遊戲，`byte_1CFDD` = `11h`，兩個玩家血量 `FFh`（`m_3_stage1_two_players`）。選單前 `byte_1CFDD` = 0，`sub_127A5` 在 `sub_12438`（開始遊戲）時才寫入。第二艘機體在前 4 秒的畫面沒有看到，未確認其位置。

### dosgolem 的缺口

`S.EXE` 的字串表有 `MY.GO ` 這樣尾端帶空白的名字。第 3 個副檔名位置留給 `sub_1C738` 改寫成 `B`，彩色模式不改寫。DOS 的路徑正規化會略過名字裡的空白（DOSBox-X `DOS_MakeName`），原版 dosgolem 找不到檔，遊戲在 `sub_1C82C` 每 16 步重試一次開檔，畫面停在密碼之後。patch 0001 補上，`TestResolveIgnoresSpaces` 在沒有 patch 時失敗、有 patch 時通過。

## 3. 影格速率與時基

收據：`fps` 腳本，A、B、C 三種配置，輸出 `fpsA`、`fpsB`、`fpsC`；另 `stage1`～`stage4` 各有 12 秒窗口（`s*_fps`）。`measure` 以虛擬秒為窗口，遊戲 tick 以 `word_273B9` 的 `+1` 計數（每次 INT 8 處理常式 `inc word_273B9`，歸零不算），幀以 `word_1CFE2` 計數，等待迴圈以 `sub_11097`（`11097h`、`1109Bh`）的執行步數計數。

| 配置 | 階段 | PIT 通道 0 | 遊戲 tick | 幀 |
|---|---|---|---|---|
| A | 標題與開場（5.0 秒） | 400.128 Hz（除數 2982） | 18.1967 Hz（91 個） | |
| A | J1 過場 | 18.2065 Hz（65536） | 18.2065 Hz | |
| A | 第一關（15 秒 ×2） | 480.154 Hz（除數 2485） | 18.1982 Hz（273 個） | 137、136 幀，9.13、9.07 幀／秒，每幀 1.993、2.007 tick |
| B | 全程 | 18.2065 Hz，從未改寫 | 18.2065 Hz | 第一關 137 幀／15.0496 秒 = 9.1033 幀／秒，每幀 2.0000 tick |
| C | 全程 | 同 B | 同 B | 同 B（步數逐位元相同：655,332,551） |
| A | 第一至四關（12 秒） | 480.154 Hz | 18.2495 Hz（219 個） | 109～110 幀，9.08～9.17 幀／秒 |

結論：

- 遊戲的時間基準是 `ASMDRV` 轉發後的 18.2065 Hz。`word_273B9` 每次 +1 的頻率在三種配置相同，與 PIT 頻率無關。`sub_11097` 等 2 個 tick，一幀 9.10 幀／秒。程式內所有關卡的幀末等待都是 `cx = 2`（`10F98h`、`13336h`、`13B59h`、`13EEEh` 前的 `mov cx, 2`）。顯示頁翻轉與幀計數一對一（A 的 137 次／15 秒）。
- `_CLK_INSTALL`（`ASMDRV` `11050h`）在 INT 60h `AX=2`（載入）時被呼叫：先 `out 43h, 36h` 把通道 0 設成除數 0（65536），用 `AH=35h` 存舊 INT 8，再以 `AH=25h` 掛 `0110:10B8`。`_CLK_UNINSTALL`（`11096h`）在 `AX=3`（停止）時還原。除數由 `1100Fh` 寫入。
- `ASMDRV` 的 INT 8 處理常式（`110B8h`）每個 IRQ0 把除數加進 16 位元累加器 `cs:1000h`，進位才用 `pushf` 加 `call far` 轉發舊處理常式（遊戲在 `A7B5h` 的那一個）。平均轉發頻率 1,193,181.8 ÷ 65,536 = 18.2065 Hz，單窗口有 ±1 tick 的抖動。轉發的是遊戲自己的處理常式，所以遊戲 tick 不跟著加快。這解釋了 A 配置 PIT 在 400～480 Hz，遊戲仍是 9.1 幀／秒。
- PIT 頻率與音樂有關：`A.MIX` 啟動時 2982（400.128 Hz），`B.MIX` 啟動時 2485（480.154 Hz）。兩個值是 4 × 速度欄（`A.MIX` 100、`B.MIX` 120）換成除數後取整數（1,193,182 ÷ 400 = 2982.9，÷ 480 = 2485.8）。等級：強推論（兩個資料點）。
- 每幀忙碌步數：第一關約 10.1 萬～13.4 萬道指令，第二關 13.2 萬，第三關 5.8 萬，第四關 4.7 萬。一幀的時間 126 萬步，等待迴圈佔 89.5%～96.3%。步數是 dosgolem 的指令數，不是週期。
- 同一窗口內 A 比 B 多出 OPL 寫入（第一關 1,520～1,699 次／15 秒），喇叭通道 42h 的寫入數相同（11,844）。

按鍵狀態表在 `線性 2748Bh + 掃描碼`，按下為 1，放開為 2。主迴圈每幀（約 110 ms）輪詢一次，狀態必須在輪詢時為 1。

### Ctrl+D 凍結的原因

`byte_10AD4`（音樂啟動）依序呼叫 `AX=0`、`2`、`4`，沒有先停止。`AX=2` 的 `_CLK_INSTALL` 讀目前的 INT 8 向量，此時已經是 `ASMDRV` 自己的 `0110:10B8`，存成「舊處理常式」。之後累加器進位時轉發給自己，遊戲的 INT 8 處理常式（`A7B5h`）再也沒被呼叫，`sub_11097` 永遠等不到 tick。正常的停止序列是 `AX=5`、`3`、`0`（`10B12h`）。這是原版程式碼的行為，等級動態已證實，原因靜態已證實（`ASMDRV` `11050h`、`11096h`、`100D5h`）。

## 7. ASMDRV

- 路徑 A：dosgolem 的監督佇列加 `int 21h AH=31h` 可以直接串接，`S.EXE` 的 `AH=4Bh` 不需要。`ASMDRV` 用 `AH=35h`／`25h` 掛 `INT 60h`（`0110:0038`，步 54,408），`AH=31h` 保留 `DX=400h` 段後結束，佇列接著載 `S.EXE`（步 211,976）。程式不需修改，dosgolem 不需修改。
- 路徑 B：不載 `ASMDRV`。`INT 60h` 回傳暫存器不變，`sub_10A90` 判定 `AX` 不等於 1，把 `10AD4h`、`10B12h` 的首位元組改成 `C3`，音樂函式變成 `retn`。配置 B 與 C 都是這條結果。
- `INT 60h` 呼叫：偵測 `AX=0`（回 1 表示 AdLib）、`AX=2`（載入音色，ES:DI）、`AX=4`（開始）；停止序列 `AX=5`、`3`、`0`。`ASMDRV` 的 INT 8 處理常式與 PIT 的作法見第 3 節。

## 8. 逐幀收據

`rs2dyn` 在每個邏輯幀的固定指令位址取樣完整遊戲狀態，一幀一行，格式是 JSON Lines。Rust 核心的 `rs2-trace` 輸出同一格式，驗收 A2 用 `tools/dos/check_trace.py --diff` 逐筆比對（忽略 `emu`）。舊的 `trace NAME`（TSV）與既有收據不變。

### 8.1 驅動命令

| 命令 | 作用 |
|---|---|
| `trace NAME full`、`trace off` | 開始與結束寫 `trace-NAME.jsonl`。取樣位址的機器碼簽章與映像不符就拒絕開始 |
| `untiltrace N`、`tracerows K` | 跑到已寫出 N 筆，或再多寫 K 筆 |
| `play F0 TOKEN...`、`play now TOKEN...` | 依逐幀輸入位元組送鍵：`01` 上、`02` 下、`04` 右、`08` 左、`10` 開火（右 Shift 按下再放開一次）、`20` 轉向（`/`）。第 i 個位元組給第 `F0+i` 筆那一幀，鍵在上一筆取樣寫出之後立刻送，方向鍵按住到位元改變為止。`HH*N` 重複 N 次，`@NAME` 在該位置存畫面 |
| `until8 IDA VAL` | 跑到 IDA 位址的位元組等於 VAL |
| `tracepc IDA [max]`、`watchw NAME IDA LEN [max]` | 執行到某位址就記暫存器與幀計數；範圍被寫入就記位址、舊新值、寫入指令的位址與幀計數 |
| `savestate PATH`、`loadstate PATH` | 存與還原整台機器與 DOS，供實驗加速。收據一律以冷啟動完整重跑為準 |

### 8.2 取樣點

取樣發生在「該位址的指令剛執行完」。每個邏輯幀（第一關是 `sub_10EEA` 的一次呼叫，第二至四關是各幀函式的一次呼叫）恰好經過一個取樣點一次。

| 關 | 位址 | 位置 | `frame` 的意義 |
|---|---|---|---|
| 第一關普通段 | `10F98h` | `sub_10F41` 結尾，`mov cx, 2`，下一道是 `call sub_11097` | 已遞增（`10F6Eh` 的 `inc`），取樣值 <= 621（26Dh） |
| 第一關頭目段 | `10FE3h` | `sub_10F9F` 結尾，同上 | 已遞增（`10FD3h`），取樣值 >= 622（26Eh） |
| 第二關 | `1333Ch`、`13390h` | `sub_132EB`、`sub_13344` 的 `inc word_1CFE2` | 剛遞增 |
| 第三關 | `13B5Fh`、`13BBBh` | `sub_13B0A`、`sub_13B75` 的 `inc word_1CFE2` | 剛遞增；頭目段（`byte_1CFDB` = 63h）取樣值釘在 475h（`13BCDh` 起超過 474h 就釘回） |
| 第四關 | `13EF4h`、`13F42h` | `sub_13EAB`、`sub_13EF9` 的 `inc word_1CFE2` | 剛遞增 |

- 第二至四關的 `inc` 在 `call sub_11097` 之後，取樣放在 `inc` 之後，使 `frame` 與第一關同義。等待迴圈不改任何追蹤欄位，所以狀態與等待之前相同。
- 第一關取樣點之後才發生的事不在該筆內：`10F26h` 在計數 26Eh 呼叫 `sub_10C3D`，`10F36h` 在計數 28Ah 把計數倒回 288h，下一次 `sub_10EEA` 開頭的 `sub_110E3`（計數 1）、`sub_11141`（計數 26Ch）與示範模式的整關重置 `sub_10E33`（計數 28Ah）。
- 取樣位址的機器碼簽章是 `B9 02 00 E8`（`mov cx, 2` 接 `call`）與 `FF 06 22 04`（`inc word ptr ds:422h`），在映像中逐一核對，不符就中止。
- 位址換算與其他收據相同：用 INT 8 向量定出映像基底，資料段位移 X 的執行期位址是基底 + `0CBC0h` + X。
- 不跳號、不重複的證據是三道：`n` 連續；`emu.incs`（追蹤開始後 `inc word_1CFE2` 的執行次數）減 `n` 在整個檔案內是常數；`frame` 逐筆加 1，例外只有頭目段回捲、示範模式重置與換關。`check_trace.py` 三項都查。

### 10.1 bullet_slot_carry

機制（靜態已證實）：

- `sub_17855` 寫敵彈格網 G2：格值 = 形狀格值 + 槽號，8 位元相加（`17888h` 的 `add al, byte_1F7DB`）。一般彈形狀格值 1，槽 15 得 10h，槽 16 到 19 得 11h 到 14h。道具形狀格值 81h、41h、C1h、21h 加槽號 15 以上會進位到高四位元，`sub_14CD4` 的 `and ah, 0F0h` 比對 80h、40h、C0h、20h 落空，判成傷害。
- 玩家判定 `sub_14C85` 讀到非 0 格，先呼叫 `sub_14D54`：`and al, 0Fh; dec al; bx = al x 2; [bx+32B3h] = 0`（`14D55h` 到 `14D62h`）。格值 10h 算出索引 FFh，寫 `32B3h + 1FEh` = `34B1h`（槽 15 記錄的 w10，也就是 y）；格值 11h 到 14h 算出索引 0 到 3，清掉槽 0 到 3 的指標。擊中的槽 15 到 19 沒被清除。

敵彈槽使用量（追蹤；`trace_stage1` 到 `4` 是秘技、不送輸入，頭目全程活著）：

| 關 | 收據 | 筆數 | 敵彈同時最大 | 最大槽號 | 槽號 >= 15 的筆數 |
|---|---|---|---|---|---|
| 1 | `trace_stage1` | 1374 | 6 | 8 | 0 |
| 1，每幀開火 | `boss1_kill` | 1192 | 6 | 7 | 0 |
| 1，展示 DM1 | `trace_dm1` | 640 | 3 | 2 | 0 |
| 2 | `trace_stage2` | 1371 | 5 | 6 | 0 |
| 3 | `trace_stage3` | 1900 | 20 | 19 | 778（普通段 251、頭目段 527） |
| 4 | `trace_stage4` | 2200 | 20 | 19 | 1162 |

敵彈池 20 槽，生成找第一個空槽，所以槽號 >= 15 的前提是同時在飛 >= 16 發。第一、二關用不到，第三、四關的頭目戰池常滿。

自然流程中的錯刪（`tools/dos/analyze_slot_carry.sh 收據/trace-sN.jsonl`：從追蹤重建 G2 與玩家 1 的判定帶，推出 `sub_14D54` 會清的槽，再與前後兩筆比對）：

| 收據 | 受擊筆數 | 判定帶讀到槽 >= 15 的格 | 其中前一筆有、這一筆沒有的槽正是程式碼要清的槽，且擊中的槽留在池裡 |
|---|---|---|---|
| `trace_stage3` | 272 | 4 | 3 |
| `trace_stage4` | 125 | 9 | 8 |

例：`trace_stage4` 幀 1366（n = 1360），槽 16 的敵彈寫了格值 11h，玩家判定帶讀到後清槽 0；槽 0 的敵彈前一筆在 (22,15)，離玩家與邊界都遠，這一筆消失，槽 16 留在池裡。幀 1406（n = 1400）槽 17 的格值 12h 清掉槽 1（前一筆在 (2,4)）。

暫存器層證據：`defect_slot_carry`（第四關，同輸入，加 `tracepc 14D54h`、`14D62h`）。`14D54h` 共 120 次，進入時 AL 是格值：10h 共 7 次、11h 9 次、12h 5 次、14h 2 次（槽 15、16、17、19 擊中玩家），其餘 97 次 AL <= 0Dh。`14D62h` 的 BX（清除的指標表位移）：格值 10h 得 01FEh（表外），11h 得 0000h，12h 得 0002h，14h 得 0006h。

自然流程中槽 15 的寫入：`defect_slot_carry` 對 `34B1h`（`20071h`）掛 `watchw`，`14D62h` 把 `34B1h` 的 `0Ah` 寫成 `00h` 共 5 次（幀 1333、1505、1753、1925、2173，BX = 01FEh）。`34B1h` 是槽 15 記錄的 w10（y），這顆敵彈的 y 在擊中玩家的那一幀被歸零。

玩家被槽 >= 15 的敵彈擊中時的行為：

1. 槽 0 到 3 的一顆無關敵彈憑空消失（格值 11h 到 14h），槽 15 擊中時沒有槽消失，但該敵彈的 y 被寫成 0。
2. 擊中的敵彈沒被刪除，無敵 6 幀結束後若仍與判定帶重疊會再次判定擊中，血量再減半（秘技開啟時血量不減，所以收據裡沒有血量變化）。

結論：缺陷。修法是槽號與形狀值分開存，不進位。第三、四關頭目戰的受擊會受影響，第一、二關不受影響。

### 10.2 armor_cell_index

機制（靜態已證實）：雷射（`16A87h`、`16B06h` 的 `mov byte_1F1C0, al`）與砲座接觸（`14B95h` 之後走 `14C23h`）記錄擊中的 G1 格值時沒有排除 `FEh`。一般玩家子彈的 `16B49h` 在 `16B88h` 排除了 `FEh`（命中但不記錄，沒有傷害）。傷害函式 `sub_16946` 把格值減 1 當槽號：`dec al`（`1694Dh`）、`bx = al x 2`、`ax = [bx+2294h]`（實體指標表）、`si = ax + 20h`、`[si] = (1 << 8) | (低位元組 + 1)`（`16955h` 到 `16974h`）。格值 `FEh` 得槽號 FDh，`2294h + 1FAh` = `248Eh`，這個位址在實體槽 9 的記錄內（`22B4h` + 9 x `30h` + `2Ah`，也就是 w21 動畫計數）。

收據 `defect_armor`（第四關，頭目圓盤，模板 `8441h`，形狀 20x8，上 3 列是 `01`，下 5 列共 90 格 `FEh`）：兩座砲座加雷射武器（`poke`），`/` 轉向朝右，每幀開火。`tracepc` 記 `1694Dh`、`1695Ch`、`16974h`，`watchw` 記 `dseg:0000h` 起 100h 位元組的寫入：

| 項目 | 結果 |
|---|---|
| `16946h` 進入時格值（AL） | `FEh` 137 次（幀 1060 到 1231，幾乎每幀），`01` 313 次，`02` 到 `0Ah` 共 337 次 |
| 格值 `FEh` 時 `1695Ch` 的 BX 與 AX | 137 次全是 BX = 01FAh、AX = 0020h，也就是 `[248Eh]` = 0，加 20h 得 SI = 0020h |
| `16974h` 的寫入 | 寫 `dseg:0020h`，每次低位元組 +1、高位元組 1（例如 `0166h`、`0167h`）。雷射路徑 `16974h` 寫 165 次，砲座接觸路徑 `14C3Ah` 寫 40 次，另有 1 次寫到 `0021h` |
| 圓盤的傷害欄（`w16` 低位元組） | `FEh` 命中期間不變：幀 1061 到 1114 全是 0，只有 `01` 格命中（幀 1117 到 1131）加到 17（`0011h`） |
| 槽 9 的 w21 | 槽 9 存活的 48 筆內全是 0，所以指標讀到 0 |

結論：缺陷，一次寫錯位址。沒有觀察到玩家看得見的行為差異：裝甲格本來就不該受傷，圓盤也確實沒受傷，被寫的 `dseg:0020h` 是 `byte_1CBE0`，只有啟動時的文字畫面函式讀寫（`sub_10297`、`sub_105D8`、`sub_10633`、`sub_10643`、`sub_10671`），關卡內不讀。槽 9 的 w21 非 0 時寫入位址會偏移到 `0021h` 之後，目前收據沒有出現。等級：動態已證實（寫入發生與位址），無玩家可見影響是觀察到的現象（強推論）。修法是 `FEh` 格不寫傷害；旗標開關在逐幀狀態上沒有差異，只差 `dseg:0020h` 起的位元組。

附帶發現：同一個收據裡，`sub_16946` 收到指向已釋放槽的格值時（`1695Ch` 的 AX = 0020h 且 BX 不是 01FAh，共 28 次，槽 0 到 6）也寫 `dseg:0020h`。原因是實體在同一幀的步驟 3 被結算釋放，當幀的 G1 格仍帶它的槽號，之後的雷射或子彈讀到格值，指標表項已經是 0。行為與 `FEh` 的寫入相同，同樣沒有玩家可見的影響。

圓盤的另一個觀察：頭目圓盤腳本 96 步後以 E0 換成自己（第 12 份文件 6.4 節），換形時傷害欄回到 0（幀 1154 的 `0011h` 在幀 1158 是 `0000h`），所以要在單一個 96 幀循環內累計超過 30 點傷害才能打倒。
